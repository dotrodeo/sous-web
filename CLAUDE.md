# sous-web

The web client for **Sous**, a shared household cooking app (recipes, meal plan,
pantry, shopping list). It's an installable PWA and the **only** client: the native
iOS app (`sous-swift`) is retired. Code comments that cite `sous-swift` files explain
where the logic came from; they aren't a spec to stay in sync with.

The backend is **soupi** (`dotrodeo/soupi`): REST plus a per-household SSE stream,
with Clerk for auth.

## Stack

Vite + React 19 + TypeScript, TanStack Query for server state, React Router,
`@clerk/clerk-react`, `vite-plugin-pwa`, `lucide-react` icons. Plain CSS, no CSS
framework. There are no tests; CI runs format, lint, build and a Docker build.

## Layout

- `src/lib/api.ts`: fetch client. It adds `Authorization: Bearer <Clerk JWT>` to
  every request and throws `ApiError` (with `status`) on non-2xx. `useApi()` binds
  it to the current Clerk session.
- `src/lib/services.ts`: typed endpoint functions, grouped by resource.
- `src/lib/types.ts`: API types. Keep them in sync with soupi's Prisma models and
  Zod schemas. soupi silently drops fields its schema doesn't know, so a field added
  here without the backend change is lost without an error.
- `src/hooks/`: query and mutation hooks. Query keys are
  `[resource, householdId, ...]` (`recipes`, `recipe`, `recipeTags`, `pantry`,
  `categories`, `plan`), plus `['user']`.
- `src/hooks/useUser.ts`: `GET /user`, falling back to `POST /user/sync` **only on
  404**. Falling back on other errors caused a request storm (sync broadcasts
  `user_update`, which refetches `['user']`), so keep that guard.
- `src/hooks/useHouseholdEvents.ts` + `src/lib/sse.ts`: SSE over fetch
  (`@microsoft/fetch-event-source`, because native `EventSource` can't send the
  auth header). Events invalidate the matching query keys. Add a case here when
  soupi gains a new event type.
- `src/pages/`: one file per screen. `src/components/`: app shell (bottom nav on
  mobile, sidebar at 900px and up), bottom sheets, icons, QR join scanner.
- `src/lib/timers.ts`: app-wide cooking timers (a small store read with
  `useSyncExternalStore` in `src/hooks/useTimers.ts`). Countdowns are computed from
  each timer's end time, because browsers throttle timers in background tabs. The
  alarm (`public/sounds/alarm.mp3`) is unlocked on the tap that starts a timer, as
  iOS requires (restored timers unlock on the next tap). Timers are saved in
  localStorage, so they survive a reload or iOS closing the app.
- Offline (#38): `src/lib/offline.ts` saves the TanStack Query cache to
  localStorage (`PersistQueryClientProvider` in `main.tsx`; household data and the
  user, 24 h) and defines the queued item patch (`PANTRY_PATCH`): optimistic,
  paused offline, run one at a time in order, retried on network errors, saved
  across reloads. Its mutationFn is registered by `OfflineSync`
  (`components/OfflineStatus.tsx`), so use `useMutation({ mutationKey:
PANTRY_PATCH })` for list check-offs. Sign-in (Clerk) needs the network, so a
  cold start offline shows `OfflineStartNotice`. Sign-out and an account change
  clear the saved copy.
- Timer alerts (web push, #22): `src/lib/push.ts` subscribes the device (on the
  first timer tap, or the Settings switch) and registers it with soupi;
  `timers.ts` registers each running timer (`PUT /timers/:id`) and cancels it when
  stopped or when the page rings it on screen. soupi pushes when a timer ends.
  `public/push-sw.js` (imported into the generated worker) shows the notification
  on Chrome/Firefox; Safari 18.4+ shows our Declarative Web Push payload itself.
  Every push must show a notification, or Safari revokes the subscription. On
  iPhone, push works only in the app added to the Home Screen.
- `public/icons/`: the logo SVGs and the PNG icons, all generated by
  `CHROME_PATH=<chrome binary> node scripts/generate-icons.mjs` from one vector
  source. `<Logo>` in `src/components/Icons.tsx` draws the same mark in the UI.
- `src/components/SaveButton.tsx`: use it for every save. Pass `onSave` returning
  the save's promise (`mutation.mutateAsync(...)`) and do the close or navigation
  in `onSaved`, which runs after the green check has shown. It handles the
  saving ring, double-submit blocking, the error ("retry") state and screen
  reader announcements. For Enter-to-save, click it through a ref.
- `src/index.css`: design tokens (`--brand`, `--ink`, `--canvas`, …).
  `src/ui.css`: layout and shared primitives. Mobile-first.

Conventions: Prettier with 4-space indent and no semicolons (2 spaces for
JSON/YAML/Markdown), single quotes, 100-char lines. UI copy is lowercase.

## Workflow

`main` is protected: every change goes through a pull request, CI (`Format, lint, build` and `Docker image builds`) must
pass, and the branch must be up to date with `main`. The rules apply to admins too,
so pushing to `main` directly is rejected.

1. Branch off `origin/main` (in a worktree, not the deploy checkout), commit, push,
   and open a PR. Every prod deploy is a release: if the PR will be deployed, bump
   `version` in `package.json` (semver) in the same PR, with
   `npm version <x.y.z> --no-git-tag-version` so the lockfile matches.
2. When CI passes, merge it with a merge commit and delete the branch. If `main`
   moved in the meantime, run `gh pr update-branch <n> --rebase` and wait for CI
   again.
3. Release: tag the merge commit and publish it:
   `git tag vX.Y.Z <merge-sha> && git push origin vX.Y.Z && gh release create vX.Y.Z --generate-notes`.
4. Deploy: `git pull --ff-only` in the deploy checkout, then follow
   [Deploy](#deploy): dev first, verify, then prod.

## Environment

`VITE_CLERK_PUBLISHABLE_KEY` and `VITE_API_BASE_URL` are **build-time**: Vite inlines
them, so each environment is its own image and changing either needs a rebuild.
Both are public by design, but the `.env.*` files also hold the tunnel token, so
never print or commit them. `VITE_API_BASE_URL` must be the soupi environment's
**public** URL, because the browser calls it directly.

## Deploy

Docker Compose, one stack per environment: `sous-web-dev` and `sous-web-prod`,
each with `web` (nginx serving the static build) and `tunnel` (cloudflared).
Container names are `sous_web_<env>_{app,tunnel}`.

- Pass `--env-file .env.dev` or `--env-file .env.prod` on **every** `docker compose`
  command.
- Rebuild only the app: `docker compose --env-file .env.<env> up -d --build web`.
  Avoid `npm run deploy`, which runs `up -d --build` for the whole stack.
- After the prod build, tag the image with the release version:
  `docker tag sous-web:prod sous-web:X.Y.Z`. Keep the last three version images and
  `docker rmi` older ones. Don't version-tag dev images.
- Roll back by pointing `prod` at the previous version's image:
  `docker tag sous-web:<prev> sous-web:prod && docker compose --env-file .env.prod up -d web`.
- The service worker is `autoUpdate` and precaches only the app shell (API and SSE
  are never cached). nginx serves `sw.js`, `index.html` and the manifest with
  `no-cache`, so clients pick up a new build on their next load.
- When a change needs a new soupi field or endpoint, deploy soupi first.
